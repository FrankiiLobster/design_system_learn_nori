INSIGHT VAULT / THIS ROUND

本轮真正推动架构变化的洞察

这些不是 Gemini 的回答摘要，而是由你的观察、怀疑、反例和认知转折触发，并在对话中被验证为有架构价值的思考资产。

你的洞察 01

宽度不是 Size，而是布局策略

“Button 的尺寸，特别是宽度很难固定死；单独一个 Button 又没有父容器，也设置不了 Fill Container。”

因此不能在 Figma 主组件里伪造 Full Width Variant。主组件保持 Hug；实例进入父容器后才设为 Fill。代码层可以保留 fullWidth Prop，因为 CSS 需要这个语义入口。

你的洞察 02

Press 态暴露了 Ghost 与 Link 的语义冲突

“See all > 出现一圈 Fill 有点怪，但只有它的 Press 态特殊处理，也觉得有点奇怪。”

问题不在 Press 样式，而在把块级 Ghost Button 和行内 Link 混成一个组件。前者需要 Fill 证明热区，后者用文字变淡保持通透；Airbnb 的箭头实体按钮则是语义迁移为 IconButton。

你的洞察 03

清空按钮是 SearchField 的反向线索

“同事想在 Input 里统一加叉号，但我觉得一般只有搜索输入框才有；想到这里，我意识到是不是这俩本来就不是一个组件？”

清空、即时检索和全圆角共同构成了 SearchField 的行为语义。它应作为独立 Component Set 存在于 Inputs 大类下，而不是被塞进基础 Input 的条件状态。

你的洞察 04

Auto-resizing Textarea 缝住了两套 Enter 心智模型

“我只想换行，结果一回车就发出去了。它保留了 Textarea 的样式，又想承载 Input 回车发送的能力。”

视觉形态会建立用户对按键行为的预期。自动增高本身没有问题，问题是没有显式说明 Enter / Shift+Enter 规则。若用于聊天，应封装为 ChatInput 复合组件，而不是伪装成普通 Textarea。

你的洞察 05

资产分类不等于业务用途

“如果又出来一个 General，什么算 General？Avatar 算 General 吗？”

分类回答“组件放在哪个柜子、核心职责是什么”，不等于“页面里什么时候调用”。Button 可以定义在 Forms & Actions，却被 Navigation 或 Overlay 页面复用；Avatar 属于 Media & Icons，不需要新造含混的 General。

你的洞察 06

同一边框里是 Slot，跨组件拼接才是容器

“Hero 有 InputGroup，但 Gluestack 好像没有；他们怎么实现 https:// 和 .com 这种场景？”

简单 Icon、文本和单位仍在 Input 同一个 Border 内，用 Affix Slot；只有 Button、Select 等独立交互组件需要共享边界、圆角塌陷和状态传递时，才需要 InputGroup 或页面级组合容器。

长对话压缩记录

本版对 Gemini 的重复解释做了合并和缩写，只省略寒暄、机械肯定和同义复述。用户疑问、反例、设计判断、实现代价、Figma/CSS/Native 差异、组件库对照和未决问题均保留；“Gluestack 的代码支持 Slot，但 Figma 资产硬编码图标”这类小切口细节也单独留档。

01 / DIRECTION

你做的不只是组件，而是在建立秩序

除了技术分类，本轮也出现了设计系统如何在一个短期 KPI 环境中生存的问题：兴趣、ROI、组织认知和增量落地必须同时被处理。

当前判断

“软件设计像新时代的建筑设计：系统性、规范、模块化、可复用性和语义逻辑，决定了数字空间能否持续生长。

来自你的思考 · 组件给你“建造东西”的感觉，但团队更容易看见短期业务交付，而不是长期复用红利。

知识地图

Agent 协作用机器执行检验规范是否可理解、可调用
成熟系统学习分类、API、行为和职责边界
开源组件库对照 Hero UI、Gluestack 等实现取舍
Nori 重构用业务需求做增量提纯，而非闭关造系统
规范沉淀把规则变成 Figma、Markdown 与代码共享上下文
组件工作的价值长期工程红利与短期业务功利之间存在天然落差
你的思考组织策略

不要把“做组件”包装成无法衡量的理想主义

组件给你秩序感和建造感，同事感受到的却可能是前期约束、额外维护和无法立即兑现的成本。冲突的核心不是“组件有没有价值”，而是收益是否在短期 KPI 里可见。

可量化的 AI 时代收益

  • Agent 一次生成的纠错时间从分钟级下降到接近零。
  • 全局 Token 或样式修改不再逐页返工。
  • 同一规范进入 Figma、Markdown 和代码后，评审与研发沟通成本下降。

候选落地方式

  • 借具体业务需求顺手提纯组件，不发起“闭关造系统”。
  • 先让 Button、Avatar、ModalScreen 等高频资产闭环。
  • 用可演示的 Agent 生成结果向团队展示复用红利。
  • 把“减少返工、减少页面漂移”记录成可复述的案例。
学习方法 01

学习方法 02

学习 Anatomy、Slots、Props、States，以及设计意图如何转成 API。
学习方法 03

02 / TAXONOMY

分类回答“放在哪里”，业务回答“怎么被调用”

本轮最大的分类争议来自 Button、Link、Avatar 和 General。最终收敛是回到 Nori 现有的五大类，不为了解释每个页面场景而不断创造新一级分类。

资产分类核心职责本轮落点
Media & Icons媒体与基础视觉元素，不承载业务交互状态。Avatar、Icon、Image、Badge。
Forms & Actions具有可点按控件或收集输入的基础交互响应。Button、IconButton、Input、Textarea、SearchField、InputOTP。
Data Display & Feedback展示信息、进度和反馈结果。Card、Tag、Toast、Progress。
Overlay通过 Z 轴、遮罩与临时生命周期中断当前任务。Modal、BottomSheet、Popover、Drawer。
Layout & Navigation构成页面骨架、分区与路由入口。Header、TabBar、Divider、Breadcrumb、Link。

给 Nori 的分类原则

按职责组件的主职责决定资产目录，而不是它当前出现在哪个业务页面。
按查找设计师需要 Input 时会去 Forms/Inputs 查找，不因 SearchField 有导航作用就放进 Navigation。
按语义Link 不是无背景 Button，而是跳转或引导文字，归 Layout & Navigation。
不造含混类如果 General 无法给出稳定职责，就不为了 Ant Design 式分类硬新增 General。
分类 × 使用同一资产可以在别的类别的页面中被调用
你的追问已形成判断

Airbnb 顶部返回与筛选按钮仍然可以复用 Forms 里的 Ghost Button

“返回”在业务上属于 Navigation，“筛选”属于 Overlay 触发器，但它们的视觉物理实现都是带块级热区的 Ghost + IconButton。资产定义和页面用途是两层模型。

资产库层

  • Button 按块级控件职责归入 Forms & Actions。
  • Link 按导航与跳转职责归入 Layout & Navigation。
  • Avatar 按媒体元素职责归入 Media & Icons。

业务调用层

  • 从 Button 目录调用 Ghost 实例，放入 Header 或 Overlay 触发器。
  • 调用不会改变组件的原始分类。
  • 页面组合负责业务语义，不是重新命名组件。
Overlay / Layout容器可以嵌套，但归属保持唯一
延续上版架构规则

Overlay 是浮层生命周期，Layout & Navigation 是可以装入其中的骨架

全屏弹窗中的 Header、Drawer 中的 Divider、多步弹窗中的 Segmented Control 都是组合案例。它们不因此变成 Overlay，也不要求 BottomSheet 把导航结构写死。

判断 Overlay

看 Portal、Z 轴、遮罩、滚动锁定、临时生命周期和关闭行为。

判断 Layout

看排版流、分区、路由、导航和页面结构职责。

03 / ARCHITECTURE

先判断交互语义，再决定组件与变体

Button 的重构把“组件名”推进到更深一层：块级动作、行内线索、图标模式、组合容器和响应式宽度各自承担不同职责。

Button Anatomy一套 Button 属性覆盖文字、图标与 Icon Only
候选组件规则Figma / Code 1:1

Icon & Text 不该是独立 Figma Component，IconButton 也不必成为另一套视觉逻辑

Hero UI 的实践表明，纯图标按钮可以作为同一 Button 组件集中的 isIconOnly 模式。它共享底层按钮逻辑，但切换后必须触发 1:1 尺寸、缩减水平 Padding，并在代码层强制要求 aria-label。

Button 基础属性

  • variant：primary / secondary / ghost / danger 等语义层级。
  • size：sm / md / lg，锁定高度、字号与图标尺寸。
  • state：default / hover / pressed / disabled / loading。
  • isIconOnly：锁定宽高比与无文字可访问性约束。

Icon Slots

  • prefix / suffix 使用 Instance Swap。
  • showPrefix / showSuffix 使用 Boolean 显隐。
  • 对应 React 的 leftIcon / rightIcon 或 startContent / endContent。
Size / Width高度是 Size，宽度是父容器下的布局策略
你的洞察可执行规则

不要把响应式宽度做成主组件变体

宽度可以由文字 Hug，也可以在页面实例中 Fill；真正必须稳定的不变量是高度、字号、图标尺寸、圆角和颜色 Token。把宽度写死为 327px，或用超大纵向 Padding 硬撑高度，都会破坏复用与代码导出质量。

Figma

  • 主组件宽度默认 Hug Contents。
  • 实例放入页面 Auto Layout 后切换为 Fill Container。
  • 不建立 isFullWidth Variant，因为主组件没有父容器上下文。

Code / Agent

  • 保留可选 fullWidth?: boolean，内部映射 w-full。
  • 高度 Fixed，纵向 Padding 不为撑高服务。
  • 底部 CTA、表单提交默认可用 Full Width；卡片内操作保持 Hug。

待核对数值

对话中出现过 md 44 / lg 52 与 md 40 / sm 32 两组高度建议，属于跨组件库语境差异。Nori 必须基于现有移动端尺寸实测后确定唯一值，不能把两套数字同时写成规范。

ButtonGroup可以是代码容器，但不应是 Figma 组合穷举
你的质疑概念分层

成熟组件库有 ButtonGroup，不代表要把“黄按钮 + 灰按钮”画成固定 Variant

代码中的 ButtonGroup 解决圆角缝合、1px 边框重叠消除，以及 size、variant、disabled 向下传递。Figma 中真正错误的部分是把具体业务排列和按钮数量硬编码成组件集。

允许定义

  • 容器组件的 API 与行为规则。
  • Attached 模式的圆角与边框策略。
  • 统一状态与尺寸下传规则。

不要穷举

  • 左右两枚、上下两枚、全宽等固定组合。
  • 三枚或 Dropdown 混排后立即失效的变体。
  • 仅用于展示的组合图应标记为 Pattern / Example。
Ghost / Link块级动作需要热区反馈，行内线索需要保持通透
你的洞察组件拆分判断

See all > 不是 Ghost Button 的例外，而是另一个组件语义

Ghost Button 有 Padding 形成的块级热区，Press 时用低透明度 Fill 反馈“按中了这个块”；Link 紧贴文字与箭头，Press 时用透明度或下划线反馈，不制造矩形视觉噪音。Airbnb 改成箭头实体按钮后，语义已经迁移为 IconButton。

Ghost / IconButton

  • 有明确块级或 1:1 热区。
  • Hover / Press 可出现背景 Fill。
  • 图标模式必须有 aria-label。

Link / LinkButton

  • 无背景 Fill，通常无大 Padding。
  • 保持文本与图标同一排版流。
  • Hover / Press 用颜色、透明度或下划线。
  • 归入 Layout & Navigation，而不是 Forms。
Avatar视觉属性留在 Avatar，业务状态与组合关系移出
Avatar 案例组件边界

第一个 Figma 组件的 36 个 Variant 可以收拢到“仅 Size 变体”

Image / Text / Placeholder 属于 Fill 内容，Border 是视觉开关，不应和 Size 做乘法。成员选择态属于业务包装，堆叠间距、最大数量与 +N 属于 AvatarGroup。

Avatar 负责

  • 尺寸、形状、Fallback、Border。
  • 内容替换与基础视觉状态。
  • 固定 1:1 尺寸契约。

移出 Avatar

  • Selected Member → UserSelectChip / AvatarSelect。
  • 重叠与 Max → AvatarGroup。
  • 业务光环、Check、Label → Wrapper。
Avatar Scale尺寸是系统契约，不是使用者自由参数
待确认 Token候选规范

补充高频尺寸，而不是允许业务手写 33px

候选阶梯为 xs 20 / sm 24 / md 32 / lg 44 / xl 56 / 2xl 88。外描边是 Avatar 的视觉属性；CSS 中重叠头像优先用 ring 或 box-shadow，避免 border 挤压总尺寸。

Shell / Slot固定外壳承载一致性，插槽承载业务变化
组件架构可写 Spec

样式多样并不全是业务必然

容器圆角、边距、背景、Header 与 Footer 位置应由 Shell 统一；具体表单、列表和长内容只进入 Body。Shell 暴露 children、footerActions 等插槽，不允许 Agent 在外壳上重复加 Padding 或覆盖圆角。

04 / INPUTS

输入框不是一个组件，而是一组职责层级

本轮把 Input 从“带 Label 和业务后缀的巨型变体集”拆成 FormControl Shell、Input 原子、Textarea、SearchField、InputOTP，以及仅在必要时出现的组合容器。

Input 治理方案FormControl 管外壳，Input 管输入框主体
你的改造计划已形成架构

合并两个臃肿组件集，把业务结构从 Input 中剥离

原先“Text Field”和“Text Field with label or caption”的拆分会导致重复维护；国家代码、下拉箭头等业务结构又被硬编码成 Variant。新的三层结构让状态与布局解耦。

FormControl 外壳

  • 垂直 Auto Layout：Label → Control Slot → Helper / Error。
  • 统一下发 Invalid、Disabled、Required 等上下文。
  • 适配顶部 Label、左侧 Label、无 Label 的页面布局。

Input 原子

  • 只负责边框、圆角、Padding、Focus Ring。
  • States：default / focus / error / disabled。
  • Sizes：sm / md / lg。
  • Prefix / Suffix 使用 Boolean + Instance Swap Slot。
State / ContentFilled 是值，不是组件交互状态
协议纠偏可执行判断

把 Value 当 Variant，会让每个尺寸和状态再乘一遍

Default、Focus、Error、Disabled 是交互状态；Filled、Empty 是数据内容。相同原则也适用于 Button：fullWidth 是布局属性，不是按钮状态；SearchField 的清空按钮显隐才是行为状态。

Textarea视觉上都是文本框，物理与按键语义不同
Native 差异组件拆分

Input 与 Textarea 不能靠“自动变高”合并

Web 的 <input> 与 <textarea> 是不同原生标签；iOS / React Native 的多行输入会切换到不同的原生机制。单行 Input 中 Enter 常是提交，多行 Textarea 中 Enter 是换行，自动增高不能改变这个底层语义。

Textarea Figma 结构

  • Root 垂直 Auto Layout，Min Height 约 80px。
  • Content Area Fill Width / Height，文字 Top-Left。
  • Footer 可放 Counter、Resize Handle、提示 Slot。
  • Label 与 Error 继续交给 FormControl。

Auto-resizing / ChatInput

  • 初始一行，随内容增高，到 Max Height 后内部滚动。
  • 底层仍是 Textarea，但业务语义是对话输入。
  • 必须明确 Enter 发送、Shift+Enter 换行。
  • 候选方案：单独封装 ChatInput，不污染普通 Textarea。
Slot / InputGroup先看边框归属，再看子元素是否具有独立交互
你的洞察边界判断

同一边框内的 Icon / Text 用 Slot；跨组件拼接才需要 InputGroup

搜索图标、密码眼睛、https://、+1 都可以进入 Input 的 Affix Slot。若右侧是真正的 Button、Select 或独立区块，并有自己的背景、Hover 与交互状态，则属于组件拼接，需要处理相邻圆角与边框重叠。

形态 1：Inline Affix

  • 共享 Input 的 Border 与 Background。
  • 子元素主要是 Icon、Text、简单单位。
  • 优先用 Input Prefix / Suffix Slot。

形态 2：Segmented Composition

  • 多个独立交互控制共享一排边界。
  • 需要圆角塌陷、边框合并、统一状态传递。
  • 使用 InputGroup 规则或页面级 Auto Layout 组合。

Nori 的 80/20 收敛

先强化 Input Slot，覆盖约 95%–98% 场景。不要照搬 Hero UI 的巨型 InputGroup 变体矩阵；只有出现多个真实业务复用、且 Agent 确实需要统一组合规则时，才建立精简 InputGroup 或仅保留 Markdown 行为规范。

Figma / Code 错位代码支持 Slot，不代表 Figma 资产真的暴露 Slot
审计细节你的发现

Gluestack 的 React 代码有 InputSlot，但 Figma 图层里仍硬编码 Icon

这说明开源库的代码和 Figma 常由不同维护者维护，会出现“代码高度可组合、Figma 资产却死板”的断层。Nori 的标准应由 Figma Instance Swap、代码 Compound Component 和 Markdown 结构三方共同约束。

Figma 应暴露

  • showPrefix / showSuffix。
  • prefix / suffix Instance Swap。
  • Slot 名称与代码 InputSlot 对应。

代码应提供

<Input>
  <InputSlot><SearchIcon /></InputSlot>
  <InputField placeholder="Search..." />
</Input>
SearchField搜索是独立行为语义，但属于 Inputs 大类
你的洞察候选规范

保留全圆角差异，并把 SearchField 做成独立 Component Set

普通 Input 的 16px 圆角更像稳定表单容器；SearchField 的全圆角、放大镜和清空按钮更像轻量即时检索入口。它们可以共用底层 Input 结构，但不能共用一个组件集的全部默认行为。

SearchField 行为

  • Value 为空时隐藏 Clear Button。
  • 有值时显示清空，点击后触发 onClear。
  • 清空后焦点回到输入框。
  • 默认 Search Icon、Placeholder 与全圆角。

Clear Button 布局

  • 绝对定位：right: 12px。
  • Input 预留固定 padding-right: 36px。
  • 文字被隐形内边距挡住，不会跑到按钮下方。
  • 不显示 / 显示 Clear 时输入区宽度不抖动。
InputOTP多格聚焦与联动足以形成独立组件
你的改造计划已形成判断

OTP 不是普通 Input 的一组 Slots，而是专有输入行为

它需要长度配置、逐格输入、自动前进、退格回退、粘贴分发和完成事件。虽然与 Input 同属 Inputs 大类，但物理结构和交互逻辑足以独立维护。

05 / OVERLAY

先统一浮层外壳，再定义任务模式

上版形成的 BottomSheet / ModalScreen 结论继续保留：容器、任务模式、业务内容和操作区必须分层。

BottomSheet统一 Shell，再用任务 Preset 表达变化
界面诊断候选规范

样式混乱属于 Shell 失守，结构混乱属于 Preset 未分组

Container、Header、Body、Footer 固定骨架；引导、筛选、长内容分别使用 prompt、selection、content 模式。Body 负责滚动约束，Footer 固定标准操作区。

ModalScreen全屏任务不是普通 Page，也不是随手拼装的 Modal
页面框架需核对代码

只保留可预期的 Header 模式

dismiss 使用右上角 X 与底部 CTA；actionable 使用左 Cancel、右 Done / Save。Header 只能由 title 与 headerMode 生成；底部主操作进入 Footer Slot；背景只使用统一 Surface / Canvas Token。

渲染与组合Overlay 负责 Z 轴与生命周期，内部内容跨类复用
技术约束组合案例

浮层“看起来在这里”，打开时应传送到 UI 顶层

Portal 负责避免 overflow 与局部 stacking context 截断。Navbar、Divider、Segmented Control 等组件保留原分类，只是作为内容进入 Overlay 插槽。

06 / PROTOCOL

状态、内容、按键与原生行为要分开建模

本轮把“画不画一个图层”继续追问到数据所有权、键盘行为和浏览器 / Native 实际渲染机制。

Forms 数据流受控和非受控是状态所有权问题
状态协议高频模式

受控模式让页面状态成为 Single Source of Truth

value + onChange 适合实时校验、组件联动、格式化输入和等待网络结果；defaultValue 适合简单表单与性能敏感场景。Input、Textarea、SearchField 都应明确采用哪种状态协议。

状态分类State、Content、Layout、Behavior 不能混成一张 Variant 表
诊断规则可执行

先问变化来自哪里，再决定表达方式

四类变化

  • State：Hover、Focus、Error、Disabled。
  • Content：Empty、Filled、Placeholder、Value。
  • Layout：Hug、Fill、Full Width、Resize。
  • Behavior：Clear 显隐、Loading、Open、Selection。

表达位置

  • State 进入 Variant 或代码状态。
  • Content 使用 Text Prop / Slot / 运行时数据。
  • Layout 使用 Auto Layout 与代码 Prop。
  • Behavior 进入交互 Spec、事件和状态机。
光标 / Selection不要画成 Figma 图层，要写成 Token 与平台行为
你的观察候选规范

“Playground 有颜色、Figma 没有画”不是缺失，而是原生渲染分工

光标和文本 Selection 由浏览器或 Native 控件绘制。把它们做成静态图层会造成假状态和图层重构；正确做法是在 Token / Guideline 中定义颜色，并让 Focus 态继续通过 Border / Ring 表达。

候选 Caret Rule

  • Caret Color 映射全局 Primary Token。
  • Selection Background 使用 Primary Subtle，透明度约 10%–20%。
  • Caret 与文本距离由原生 Text Layout 管理，不单独定义。

代码落点

  • Web：caret-color。
  • React Native：原生选择颜色参数或主题映射。
  • Figma：删除静态光标和全选图层。
Enter Contract同一个按键不能因视觉自动增高而悄悄改变含义
行为合同待 Nori 验证

普通 Textarea 与 ChatInput 必须写清按键规则

普通 Textarea 默认 Enter 换行；即时对话组件常采用 Enter 发送、Shift+Enter 换行。后者应显式说明行为，必要时在输入区提供轻量提示或可配置模式，不能只靠用户试错。

07 / HANDOFF

Figma、React、Native 与 Agent 说的是同一套结构吗？

本轮新增了设计师理解代码所必需的平台映射：HTML 是原生材料，React/JSX 是组件积木，iOS/Swift 与 React Native 则决定输入控件如何落地。

01

Figma Structure

原子组件、Auto Layout、Variables、Instance Swap 与代码结构 1:1，不用静态图层假装原生行为。

02

Machine-readable Output

通过 Figma API、MCP 或插件导出结构与 Token；截图只作为视觉补充。

03

Markdown Source of Truth

组件 Markdown 记录 Anatomy、Slots、Props、States、Behavior、A11y 和排他约束。

04

Code & Agent Test

Figma 与代码同名，让 Agent 能定位实例、调用 Compound Component，并用约束测试反向发现规范缺口。

Figma 概念React / Code 对应设计判断
Variantsize / variant表达稳定语义枚举，不为布局上下文造伪变体。
BooleanshowPrefix / isDisabled表达显隐、可用性和简单模式开关。
Text Propertyplaceholder / label表达可替换文案，不进入变体乘法。
Instance SwapleftIcon / InputSlot表达 Slot 或嵌套组件替换，保持自由组合。
Auto Layout FillfullWidth / w-fullFigma 在实例层切换，代码层保留响应式 Prop。
React / HTMLJSX 看起来像 HTML，但本质是组件树语法
平台基础设计师需知

HTML 是浏览器最终读懂的原生骨架，React 是可复用组件组合

浏览器原生标签固定且基础；React 把 HTML、CSS 与 JavaScript 逻辑封装成 <Button>、<InputSlot> 等自定义组件。运行时仍会映射回浏览器或 Native 能理解的结构。

对设计系统的影响

  • Figma Component 与 React Function Component 是同一抽象思路。
  • Nested Instance 对应组件嵌套。
  • Compound Pattern 把结构、行为与样式拆给多个协同组件。

Agent 读取结构

  • 组件名、Props、Slots 比截图更可执行。
  • 语义化 HTML 影响 SEO 与无障碍。
  • Markdown 应明确哪些是原生行为，哪些是业务封装。
Web / iOS / RN平台决定基础控件，框架决定封装方式
参考模型需核对团队技术栈

同一设计概念，在不同平台的底层控件并不相同

场景WebiOS / React Native
单行输入<input>UITextField / TextInput
多行输入<textarea>UITextView / TextInput multiline
界面工具HTML + CSS + React / JSSwiftUI / UIKit 或 React Native
统一程度语义与行为受浏览器影响。原生行为、焦点和 Selection 受平台影响。
Icon Swap 色彩继承替换后掉色，是图层结构或 Token 绑定失效
Figma 诊断修复规则

Figma 的 Override 依赖可匹配的子图层，不是永久记住“白色”

旧 Icon 与新 Icon 的矢量层级、图层名或颜色绑定不一致时，实例替换会丢失颜色覆盖。应统一 Icon 库的图层命名与扁平结构，并优先通过组件级 Color Style / Variable 控制颜色。

Agent Spec 示例把本轮 Input 决策写成可执行约束

  • Markdown 负责 API、行为、A11y 和边界。

08 / REVIEW

本轮知识已经进入正确层级了吗？

下轮继续更新时，Inputs 可以从一级主题内部继续分化；只有出现新的核心问题、术语、规则和验证方式时，再提升为独立主题。

已形成的判断 8 items

分类 ≠ 使用

组件在资产库有唯一职责分类，在页面中可以被 Navigation、Overlay 等场景复用。

Button 只保留一套视觉逻辑

Icon Only 是模式，不复制一套 IconButton；图标通过 Boolean + Instance Swap。

宽度不是 Variant

Figma 主组件 Hug，实例 Fill；代码保留 fullWidth Prop。

ButtonGroup 不等于组合截图

定义代码容器和边界行为，不在 Figma 穷举业务排列。

Ghost 与 Link 分离

块级热区用 Fill 反馈，行内线索用文字变淡或下划线。

Input 与 FormControl 分层

Label、Caption、Error 由外壳管理，Input 只负责输入主体。

SearchField 独立

即时检索、Clear、全圆角与 Input 同属 Inputs 大类，但独立 Component Set。

Textarea 独立

底层标签、Enter、高度与滚动行为不同于单行 Input。

需要验证的假设 8 items

五大分类是否正式采用

Forms & Actions、Layout & Navigation 是否与现有 Figma 目录完全一致？

Button 精确尺寸

sm / md / lg 的高度、Padding 和 Icon Size 需要基于 Nori 实测锁定唯一 Token。

InputGroup 是否实现

先观察真实需求频率；没有多起复用案例时只保留 Markdown 组合规则。

SearchField 命名与状态

SearchField / SearchInput 的命名、Clear 交互和全圆角是否成为正式规范？

ChatInput 边界

是否建立独立复合组件，Enter / Shift+Enter 是否可配置？

Caret / Selection Token

颜色、透明度、各平台映射和深色模式仍需真实实现验证。

Figma Slot 执行一致性

Icon、Text、Button 等 Slot 的 Instance Swap 与代码 Compound Pattern 能否保持 1:1？

平台覆盖范围

Nori 当前优先 Web、iOS、React Native 还是多端统一？这会改变 Textarea 与 OTP 规范。

下一轮动作 6 items

搭 Button Component Set

收敛 variant、size、state、prefix / suffix、isIconOnly，并实测宽度与高度。

搭 FormControl + Input

先实现两个最小闭环组件，验证 Label、Error、Slot 与 Agent 生成。

补 Textarea / SearchField / InputOTP

共用 FormControl，但不合并行为不同的 Component Set。

写组件 Markdown

至少覆盖 Button、Input、SearchField 与 ChatInput 的 States、Slots、行为与排他规则。

建立 Icon Swap 质量检查

统一矢量图层命名、扁平结构与颜色 Variable，消除替换后掉色。

用 Agent 做约束测试

让 Agent 仅根据 Figma + Markdown 生成搜索框、全宽 CTA 和 AI 聊天输入。

本轮重组结果

Input 从原来可能散落在 Forms 与 Protocol 的小点，提升为独立的一级主题域；Button、Link、IconButton 和 ButtonGroup 归入组件架构；React / HTML / iOS / Textarea 平台映射并入 Figma → Agent 交接；上一轮的 Overlay 主题保持独立但不再吸收本轮输入内容。长对话中没有价值的寒暄被省略，所有能影响组件判断的细节都保留了落点。
