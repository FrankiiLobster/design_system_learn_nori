02 / TAXONOMY

分类是行为边界，组合是使用关系

Overlay 与 Layout & Navigation 可以互相嵌套，但分类归属由组件的核心责任决定，不由它出现在哪个页面决定。

维度OverlayLayout & Navigation
空间关系Z 轴浮层，脱离正常文档流。XY 轴骨架，构成页面物理结构。
生命周期临时中断任务，打开后关闭返回。常驻页面框架或路由入口，不打断主流程。
渲染机制Portal、Backdrop、Z-index、焦点与滚动管理。Document Flow、Header、Tab、Divider、Grid/Stack。
组合关系提供 Header / Body / Footer 等插槽。可作为内容插入 Overlay 插槽，不改变自身分类。

给 Nori 的边界原则

先看职责有 Portal、遮罩、浮层动画与临时生命周期，归入 Overlay。
再看组合Overlay 内部可以放 NavigationBar、Divider、Forms、Avatar。
反向约束页面不能静态内嵌 Overlay，必须由事件触发它的生命周期。
金句重叠来自组合，不应复制一套分类或组件。
分类 × 组合组件可以跨类协作，但归属仍然唯一
已形成判断架构规则

Overlay 是容器，Layout & Navigation 是装进去的骨架

全屏弹窗中的 Header、Drawer 中的 Divider、多步弹窗中的 Segmented Control 都是组合案例。它们不因此变成 Overlay，也不要求 BottomSheet 把导航结构写死。

正确组合

Overlay 暴露 Header、Body、Footer 插槽；业务在插槽内放入导航、布局或表单组件。

给 Agent 的分类规则

按 Portal / Z 轴 / 遮罩 / 动画判断 Overlay；按排版、分区、路由判断 Layout & Navigation。

03 / ARCHITECTURE

先决定边界，再决定加不加变体

新内容把组件问题从“画几个 Variant”推进到单一职责、组合结构、复用范围和尺寸契约。

Shell / Slot固定外壳承载一致性，插槽承载业务变化
组件架构可写入 Spec

外壳规则标准化，内容通过 Compound Components 扩展

样式多样并不全是业务必然。容器圆角、边距、背景、Header 与 Footer 位置应由 Shell 统一；具体表单、列表和长内容只进入 Body，不应覆盖外壳样式。

Shell 固定项

  • 圆角、背景、阴影、边距使用统一语义 Token。
  • Header 统一 Drag Handle 或 Close Button 规则。
  • Footer 只使用标准按钮布局组合。

Slot 可变项

  • children 承载 Body 业务内容。
  • footerActions 承载标准操作区。
  • 禁止 Agent 在外壳上重复加 Padding 或覆盖圆角。
Base / Wrapper通用视觉状态进基础组件，业务交互状态进包装组件
Avatar 案例判断原则

Avatar 不应该因为某个流程可选中，就长出选择态

把 isSelected 塞进 Avatar 会污染静态媒体展示职责，也会让尺寸、状态、外圈组合成指数级 Variant。成员选择应使用 UserSelectChip 或 AvatarSelect 包装 Avatar。

加入 Base Component

Hover、Focus、Disabled、Loading 等通用状态；形状、描边、尺寸等纯视觉属性；内部结构不发生破坏性变化。

建立 Wrapper / Composite

Selected member、Unread Story、Cart added 等业务状态；需要额外 Label、Check 或光环结构；只用于少数流程。

Avatar 视觉边界描边属于 Avatar，堆叠关系属于 AvatarGroup
候选规范Figma/CSS 差异

白色外描边是通用视觉样式，成员选择态才是业务组件

外描边用于复杂背景或多头像重叠时的视觉切割，不承载业务语义，可以直接成为 Avatar 的视觉属性；重叠间距、最大数量和 +N 截断应由 AvatarGroup 管理。

Avatar / AvatarGroup 分工

  • Avatar：形状、尺寸、Fallback、Border。
  • AvatarGroup：Negative Spacing、Max、+N。

CSS 实现约束

Figma 的 Outside Border 与 CSS border 行为不同。Agent 实现重叠头像时优先使用 ring 或 box-shadow，避免挤压头像总尺寸。

Scale / Constraint尺寸不是使用者的自由参数，而是设计系统契约
待确认 Token已形成原则

禁止手改 Avatar 尺寸，改用受约束的 T-shirt Scale

20–32px 是头像与文本混排最密集的区域。现有 24 / 44 / 56 / 88 阶梯存在断层，因此建议补充高频尺寸，而不是允许 width: 33px 之类的硬编码。

候选标准尺寸

xs 20 / sm 24 / md 32 / lg 44 / xl 56 / 2xl 88

约束与例外

Figma 固定组件尺寸，Markdown 明确“只用语义 Size”。特殊场景先申请新增标准 Size，不能让业务自由覆盖。

04 / OVERLAY

先统一浮层外壳，再定义任务模式

Bottom Sheet 与 Modal Screen 的混乱来自把容器、业务内容、导航模式和操作区混在同一个组件里。

BottomSheet统一 Shell，再用 Prompt / Selection / Content 表达任务
11 个界面诊断候选规范

Bottom Sheet 样式混乱，是外壳失守与场景未分组同时发生

圆角、Margin、Header、Footer 不统一属于规范问题；引导、筛选、长详情混在同一内容结构属于抽象不足。二者应分别通过 Shell Rules 与 Preset Variants 收拢。

标准 Shell

  • Container、Header、Body、Footer 固定骨架。
  • 外壳只能用统一 Token，不允许业务覆盖。
  • Body 负责滚动约束，Footer 固定操作区。

3 个任务 Preset

  • prompt：引导、确认、单步操作。
  • selection：表单、日历、列表选择。
  • content：长内容与多段 Snap Points。
ModalScreen用两种 Header 模式收拢全屏任务型与编辑型页面
页面框架需核对现有代码

全屏弹窗不是普通 Page，也不是可以随手拼装的 Modal

它拥有独立页面能力，但生命周期仍属于 Overlay。应固定 Header / Body / Footer 三段框架，并在设计系统层只保留两种可预期的 Header 模式。

两种标准模式

  • dismiss：右上角 X，底部固定 CTA。
  • actionable：左 Cancel、右 Done / Save。
  • 容器再区分 full 与 pageSheet。

Agent 排他规则

  • Header 只能由 title + headerMode 生成。
  • 底部主操作必须进入 Footer Slot。
  • 背景只允许使用统一 Surface / Canvas Token。
渲染与组合Overlay 负责 Z 轴与生命周期，内部内容保持跨类复用
技术约束组合案例

浮层“看起来在这里”，打开时应传送到 UI 顶层

Portal 负责避免 overflow 与局部 stacking context 截断。Navbar、Divider、Segmented Control 等组件仍保留原分类，只是作为内容被放进 Overlay 插槽。

渲染约束

  • 挂载全局 Portal / root layer。
  • 声明 Z-index、Backdrop 和滚动锁定。
  • 声明遮罩、ESC、Android 返回键关闭规则。

典型组合

  • Modal Header 内放 NavigationBar。
  • Drawer Body 内放 Divider / Stack。
  • 多步 Modal 内放 Steps / Segmented Control。
05 / PROTOCOL

状态和数据流，是设计规范的另一半

视觉稿里的一个“Disabled”或“Open”，在代码里对应的是数据拥有权、回调协议和交互边界。

Forms 组件Input、Checkbox、Select、Switch
状态协议高频模式

专业组件库通常同时支持两种模式，但业务常优先受控

受控模式让页面状态成为 Single Source of Truth，适合实时校验、组件联动、输入格式化和等待网络结果后再改变状态。非受控模式更适合简单表单或性能敏感场景。

受控

value + onChange。组件展示什么，由外部状态决定；组件只发出变化通知。

非受控

defaultValue。组件内部管理状态，外部在提交时读取结果，使用成本更低。

状态完整性从“有几个变体”转向“状态是否可执行”
诊断方法需落 Nori

状态不是装饰，而是组件的行为合同

Button、Input 或 Sheet 的状态应同时对应视觉表现、交互结果和数据约束。Agent 漏掉 Disabled、Error 或 Loading，不只是产出问题，也可能说明 States 规范不完整。

建议统一检查的状态面

  • 通用状态：default、hover、pressed、focused、disabled、loading。
  • 表单状态：invalid、required、readOnly、value / empty。

状态如何写进 Agent API

每个状态要说明外观、交互结果、状态拥有者、触发条件和恢复方式，不能只留一个 Figma Variant 名称。

06 / HANDOFF

Figma、Markdown 与代码各自承担什么

视觉标注主要给人看；Agent 需要结构化 Figma 输出、项目内 Markdown 和与代码 1:1 对齐的命名。

01

Figma Structure

Figma 只保留原子组件与变体；100% 使用 Auto Layout 和 Variables / Tokens，组件命名与代码 1:1。

02

Machine-readable Output

通过 Figma API、MCP 或插件导出 Structure / Tokens。截图 + Vision 作为补充，而不是规范源。

03

Markdown Source of Truth

为每个组件维护代码库内 Markdown。视觉变化改 Figma，规则与 API 变化改组件 Markdown。

04

Code Mapping & Test

保证 Figma Component 与代码 Component 同名，让 Agent 能定位实例、调用组件并接受约束测试。

# nori/components/Avatar.md

component: Avatar
category: Media & Icons
figma_component: Avatar
code_component: <Avatar />

sizes:
  xs: 20
  sm: 24
  md: 32
  lg: 44
  xl: 56
  2xl: 88

visual_props:
  shape / fallback / badge / outsideBorder

  selection: UserSelectChip
  overlap: AvatarGroup

constraints:
  - never set custom width or height
  - use ring / box-shadow for outside border
  - keep business selection outside Avatar
