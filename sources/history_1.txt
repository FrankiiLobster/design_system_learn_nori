首先，这种组件应该叫什么？Modal？Drawer？


gemini response

在现代 UI 规范体系和代码库（如 Hero UI、Shadcn UI、Material Design 等）中，这种组件最标准的命名是 Bottom Sheet，或者 Modal Sheet。

它既不是典型的 Modal（弹窗），也不是典型的 Drawer（抽屉）。


三种组件的区别与定义

Bottom Sheet（底部滑出卡片）： 专门用于移动端的模态容器。它从屏幕底部向上滑出，带有圆角，覆盖部分或大部分屏幕，背景带有遮罩（Scrim/Dimmed），通常用于引导流程、分步操作或选择器。
Modal / Dialog（对话框/弹窗）： 通常居中浮现在屏幕正中间，四周留白，用于强提醒、确认操作或短小的交互。
Drawer（抽屉）： 传统上多指从屏幕左侧或右侧边缘滑出的侧边栏（如 Navigation Drawer），或者在桌面端占满单侧的面板。


给 Agent（Codex 等）定义时的建议命名

为了让 Agent 在写代码和理解 Figma 变体时不产生混淆，建议在 Nori 设计系统中使用以下命名策略：

首选命名： Bottom Sheet 或 Sheet
组件分类： 归类在 Overlays / Dialogs 目录下。
变体 (Variants) 参数建议：type: bottom (移动端常用) / center (切换为居中 Modal) / side (侧滑)
hasOverlay: true / false
dismissible: true / false (点击背景或关闭按钮是否可关闭)

gemini response

gluestack-ui 的这种分类方式正是业界最标准的 功能性分类（Functional Categorization）。

将组件按功能分类，不仅能让设计师快速查找，更重要的是它建立了一套 心理模型（Mental Model），帮助 Agent 理解“这个组件在 UI 层级和交互中扮演什么角色”。

行业通用的 6 大基础分类体系结构如下：

分类名称 (Category) 核心职责 (Core Responsibility) 典型组件 (Typical Components)
Forms (表单/输入) 收集用户输入的数据，处理各种交互输入状态。 Button, Input, Checkbox, Radio, Select, Switch, Slider
Data Display (数据展示) 向用户展示静态或动态信息、状态以及数据集合。 Badge, Card, Avatar, Table, Tag/Chip, List
Feedback (反馈/提示) 针对用户的操作或系统状态变化，向用户提供即时反馈。 Alert, Toast, Progress, Spinner/Skeleton
Overlay (层叠/浮层) 盖在主页面内容之上的临时浮层，要求用户聚焦或提供上下文操作。 Modal, BottomSheet, Drawer, Popover, Tooltip, Menu
Disclosure (信息显隐/折叠) 控制非核心信息的显示与隐藏，帮助收纳空间。 Accordion, Collapsible, Tabs
Navigation (导航) 引导用户在应用的不同视图、页面或层级间跳转。 Navbar, Bottom Navigation, Breadcrumb, Pagination


为什么这种分类结构对 Agent 非常重要？

确定 UI 层级关系（Z-Index & Render Order）：如果 Agent 知道一个组件属于 Overlay，它会自动推断出这个组件需要包裹在 Portal 里，且渲染层级高于标准页面元素。


规范交互行为（Interaction Expectations）：Disclosure 类组件通常包含 isExpanded 或 isOpen 的布尔值状态；Forms 类组件必然绑定 onChange、value 和 disabled。


架构语义映射（Token Mapping）：Feedback 类的组件（如 Alert、Toast）会高度绑定语义化颜色 Token（如 color-status-success, color-status-error），而 Forms 类组件更依赖 color-border-focus 或 color-bg-hover。

在整理 Nori 现有组件库时，可以直接采用这套标准大类作为 Figma 文件架构和 Markdown 规范目录的底层框架。

gemini response

这是一个非常敏锐且关键的问题，直接触及了设计系统分类学（Taxonomy）的核心分歧。

这两个疑问可以拆解为两部分：概念的包含关系，以及分类视角的差异。


1. Actionsheet 和 Bottom Sheet 是同一个东西吗？

Bottom Sheet 是“容器形态”，Actionsheet 是“特定业务场景”。

Bottom Sheet（底部滑出面板）： 这是一个通用容器。里面可以装任何东西，比如分步表单、复杂的筛选器、富文本、甚至一个包含很多控件的复杂 Card。
Actionsheet（操作列表）： 它是 Bottom Sheet 的一种特定用途子集（源自 iOS 的 UIActionSheet 概念）。它的内容非常标准化——通常就是一列针对当前上下文的可选操作按钮（如：拍照、从相册选择、删除、取消）。

简单来说：所有 Actionsheet 都是 Bottom Sheet，但 Bottom Sheet 不止包含 Actionsheet。


2. 为什么 gluestack 把它归在 Disclosure？而大多系统归在 Overlay？

归类的不同，源于组件库团队设计分类时的核心视角不同：

视角 A：基于“交互意图/行为”（Disclosure 视角 —— gluestack 的做法）

Disclosure（揭示/显隐）： 这个词在 UX 里的核心意图是“逐级揭示信息（Progressive Disclosure）”。
gluestack 团队认为：用户点击某个按钮，系统向用户“揭示（Disclose）”出更多补充操作或次要信息。因此他们从 UX 行为逻辑出发，把 Actionsheet、Accordion（手风琴）放在了一起。

视角 B：基于“渲染架构/视觉层级”（Overlay 视角 —— 业界主流 & 我建议给 Agent 的做法）

Overlay（浮层/覆盖）： 这个词的核心是 DOM / 渲染层级。
绝大多数 UI 库（如 Material Design, Hero UI, Chakra UI）认为：不论你叫 Modal、Drawer、Actionsheet 还是 Tooltip，你们在技术实现上的共同点都是脱离当前文档流、渲染在 Z 轴最高层（Portal）、带有黑色遮罩 Backdrop。


为什么建议在 Nori 规范中将它归为 Overlay？

如果你要让 Agent (Codex/Cursor) 编写代码或做 UI 布局，Overlay 视角远优于 Disclosure 视角：

如果 Agent 看到分类是 Overlay，它能立刻准确推断出代码结构：需要挂载在根节点 <Portal> 下。
需要处理 Z-index 优先级。
需要处理遮罩层点击事件（closeOnOverlayClick）。
需要处理 ESC 键或 Android 返回键响应。


如果归类在 Disclosure，概念就太泛了（因为手风琴折叠面板 Accordion 也在里面，但 Accordion 完全不需要遮罩层和 Portal）。

所以，gluestack 的分类偏向“UX 概念分类”，而在建立给 AI 看的架构规范时，采用 Overlay (底层渲染特性) 更加清晰无二义性。

你刚才提到的Portal 挂载、受控/非受控模式是什么意思？


gemini response

这两个概念是从前端工程（React / Vue / React Native 等）中借用过来的，但它们在 UX 设计和设计系统制定中，直接决定了组件在不同上下文中的行为逻辑和设计稿落地到 AI/代码时的完备度。


1. Portal 挂载（Portal / Portaling）

物理层面的意思： 
在网页或 App 的 HTML/UI 结构树中，组件通常是按照层级嵌套的（比如：页面 -> 列表 -> 列表项 -> 按钮）。但 Portal（传送门）机制允许一个组件在代码逻辑上写在嵌套最深的地方，但在渲染时直接“传送”到整个 UI 树的最外层（通常是 <body> 的顶部）。

为什么要用 Portal？（UX 与开发痛点）：
如果一个 Modal（弹窗）或 Tooltip（提示框）不用 Portal，而是直接渲染在列表项内部，就会遇到两个灾难性的问题：

层级截断（overflow: hidden）： 如果外层卡片设置了超出隐蔽，弹窗就会被切掉一半。
Z-Index 层级混乱： 即使给弹窗设了 z-index: 999，如果它的父元素 z-index 很低，它依然会被同级的其他卡片盖住。

给 Agent 规范的意义：
当你定义一个组件为 Overlay（浮层）大类时，就是在告诉 Agent：“这个组件打开时必须开启 Portal，脱离当前页面父级容器，直接渲染在最顶层，且背景加上遮罩遮挡下方所有的交互。”


2. 受控与非受控模式（Controlled vs Uncontrolled）

这是指组件的内部数据/状态（ State ），到底由谁说了算。

非受控模式（Uncontrolled / 自给自足型）：

意思： 组件自己管理自己的状态，外部不需要关心它的内部细节。
例子： 一个简单的原生 <input /> 框，你在里面打字，字就显示出来了，外部页面只需要在提交表单时去“拿”它的结果。或者一个简单的 Accordion（手风琴），点击展开/收起完全由组件内部自己搞定。
特点： 使用简单，开箱即用，但外部很难干预它的行为。

受控模式（Controlled / 傀儡听话型）：

意思： 组件自己不保留状态，它的展示完全由外部传入的数据（value 或 isOpen）驱动，同时当用户试图修改它时，它只负责发出通知（如 onChange 或 onClose），改不改由外部页面说了算。
例子： 一个 Switch（开关）组件。你点了它，它自己不会自动变成打开状态；它会触发 onValueChange 通知页面：“用户点我了，你要不要把数据改成 true？”
只有当外部页面把数据改成 true 并重新传回给 Switch 时，Switch 才会切到“开”的状态。


特点： 灵活性极高。比如当用户点击开关时，系统需要弹出一个确认框询问“确定要关闭吗？”，或者需要等网络请求成功后才能切换开关状态——这种复杂逻辑必须要求组件是受控的。


总结：设计规范中的对应关系

概念 核心解决的问题 Figma / 设计规范中的体现 写给 Agent 的规范约束
Portal 挂载 视觉遮挡与渲染层级冲突 浮层组件（Modal/Sheet/Tooltip）独立于 Page Frame 存放，声明全局遮罩。 isPortal: true, 指定 Z-Index 策略与 Body 滚动锁定。
受控 / 非受控 交互状态的控制权与数据流 规范 Component 的 API 属性（如 value vs defaultValue，isOpen vs defaultIsOpen）。 声明组件是否暴露状态回调（如 onOpenChange），以便 Agent 编写复杂业务逻辑。

那你刚才提到的Forms类型组件，一般是受控还是非受控呢？


gemini response

答案是：专业的 UI 组件库在工程实现上，Forms 类组件通常同时支持“受控”与“非受控”两种模式，但在实际业务开发以及 Agent 写代码时，绝大多数场景都会使用“受控模式”。

为了让你在做设计规范（Spec）时逻辑更严密，我们可以把 Forms 类组件（Input、Checkbox、Select、Switch 等）在这两种模式下的本质区别拆解一下：


1. 为什么 Forms 组件首选“受控模式”？

Forms 类组件的核心使命是收集数据并进行业务校验。在现代 Web/Mobile 开发（如 React/Vue/React Native）中，如果使用受控模式，数据的“单一事实来源（Single Source of Truth）”就在页面状态中，这带来了极大的灵活性：

实时校验（Real-time Validation）： 用户每输入一个字符，页面就能立刻判断“密码强度是否足够”或“邮箱格式是否正确”，并实时改变 Input 组件的 error 状态。
联动逻辑（Component Linkage）： 比如点击 Switch（开启优惠券），下面的 Input（输入优惠码）才从 Disabled 变为 Enabled；或者选择了“中国”，下一个 Select 才会动态加载“省份列表”。
格式化与限制（Input Masking）： 比如用户在输入手机号时，受控模式可以实时把 13800138000 格式化为带空格的 138 0013 8000，或者直接限制用户无法输入英文字母。


2. 什么时候会用到“非受控模式”？

非受控模式在 Forms 组件中主要用于极简场景或性能极致优化场景：

一次性简单表单： 比如一个简单的“搜索框”或“反馈文本框”，页面不需要关心用户打字的中间过程，只需要在用户点击“搜索/提交”那一刻去拿到最终文本。
超长复杂表单（性能考量）： 如果一个页面有几百个输入框，采用受控模式可能会导致用户每打一个字整个大页面都重新渲染（Re-render）造成卡顿。非受控模式可以避开这个性能瓶颈。


3. 给 Agent（Codex 等）写规范时的 Spec 建议

当你在 Nori 设计系统里定义 Forms 类组件（比如 Input 或 Switch）的属性（Props）时，为了让 Agent 理解并写出优雅的代码，建议在规范文档中做如下标准定义：

提供配对属性（Value vs DefaultValue）：受控属性：value（当前值） + onChange / onValueChange（值改变时的回调）
非受控属性：defaultValue（初始默认值）


显示声明状态驱动 Props：声明组件应该接收 isInvalid（校验是否失败）、isDisabled（是否禁用）、isRequired（是否必填）等布尔属性。

Agent 认知逻辑总结：

只要在 Spec 里声明了这个 Forms 组件支持受控模式，Agent 在生成代码时就会自动用 useState 或表单库（如 React Hook Form）来绑定这个组件的状态，实现精准的数据控制与错误提示。
